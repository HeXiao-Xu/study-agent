## 第 0 章 先读这一章：AI 协作开发的铁律

这 13 条是从无数"AI 写崩项目"的教训里提炼的，**违背任何一条，两周内必然返工**。

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **契约先行**：先把数据表结构（SCHEMA.md）和接口清单（API.md）写下来，再让 AI 写实现 | AI 没有契约就会自由发挥，前后端对不上，模块之间互相打架 |
| 2 | **一次一个任务卡**：单次会话只让 AI 做一件半天内能做完、能验收的事 | 一次给 5 个需求，AI 会挑简单的做，剩下的半成品混进代码 |
| 3 | **每步可运行**：任何时刻 `git pull` 下来项目都能启动 | 长时间"半成品状态"是灾难，报错会叠加到无法定位 |
| 4 | **不相信"已完成"**：AI 说完成不算完成，跑验收命令、点界面、看数据库才算 | AI 会"汇报式完成"——文件建了、函数写了、但没跑通 |
| 5 | **小步提交**：一个任务卡一个 commit，commit message 写清做了什么 | 出问题能 `git revert` 回退，也方便写论文工作量说明 |
| 6 | **禁止顺手重构**：明确告诉 AI"只改这几个文件，不要动其他地方" | AI 的"优化"会波及已完成模块，把你昨天的成果改坏 |
| 7 | **关键算法自己读懂**：RRF、掌握度更新、组卷打分，必须能对着代码讲出来 | 答辩老师会问实现细节，"这是 AI 写的"会直接失分 |
| 8 | **不把密钥给 AI**：API Key 只放 `.env`，`.env` 进 `.gitignore` | 泄漏风险 + 提交历史污染 |
| 9 | **不让 AI 造假数据**：自测用例、抽查结果、问题记录必须真实 | 学术诚信红线，代价是毕业 |
| 10 | **报错给原文**：贴完整堆栈 + 相关代码 + 你期望的现象，别只说"报错了" | 信息不足时 AI 会瞎猜，改错地方浪费一小时 |
| 11 | **前端与后端分开做**：先做后端接口并用 curl/HTTPie 自测通过，再做前端页面 | 前后端一起做，出问题不知道怪谁，调试成本翻倍 |
| 12 | **文档跟着代码走**：每个任务完成后更新 PROGRESS.md / API.md | 仓库文档就是 AI 的长期记忆，文档滞后 = AI 下一轮开始瞎编 |
| 13 | **能用现成的就别自己写**：新需求先问"有没有成熟库/API"，有就直接用 | 你只有 8 个月，重复造轮子是最贵的浪费 |

### 第 13 条展开：复用优先（这条能帮你省下 1/3 的时间）

**判断标准：这个库会不会接管我的主流程？**

| 类型 | 态度 | 例子 |
|---|---|---|
| 原子能力库 | ✅ 直接用 | PyMuPDF、jieba、KaTeX、tiktoken |
| 基础设施 | ✅ 直接用 | Docker、PostgreSQL、Redis、MinIO、Nginx |
| 业务脚手架 | ✅ 直接用 | FastAPI、SQLAlchemy、Element Plus、Playwright、APScheduler |
| 接管主流程的框架 | ⚠️ 谨慎，最多用在 Agent 层 | LangChain 全家桶、LlamaIndex |

**三个判断问题**（任一条答"不能"，就换掉或自己写）：

1. 它出错时，我能看到中间结果吗？
2. 我要改它的默认行为时，容易吗？
3. 论文里我能说清"这一层我做了什么"吗？

**本项目必须自己写的只有 9 块**（论文创新点所在）：切片策略、混合检索与 RRF 融合、上下文组装与引用校验/拒答、知识点对齐打分、错因诊断与题目复算自检、掌握度模型与遗忘调度、自适应组卷、Agent 工具与状态机、自测用例与抽查脚本。

**给你的下任务卡话术**：在每张任务卡的提示词开头加一句 ——

```
本任务优先复用成熟库/API，不要自己实现已有成熟方案的功能。
如果你打算自己写某个通用能力（分词、解析、分页、认证、定时、PDF 渲染等），
请先停下来告诉我：有没有现成的库可以用？推荐哪个？为什么？
```

### 判断 AI 是否在糊弄你（出现任一，立刻停下来追问）

- 说"已完成"但没给出**运行/测试命令和输出**
- 一次性改了 8 个以上文件，却说不出每个文件为什么改
- 用了仓库里不存在的依赖、字段、函数名（**幻觉 API**）
- 把功能"简化"了但没告诉你（比如说好的 RRF 融合变成了单纯向量检索）
- 报错时把 `try/except: pass` 加上就说"修好了"
- 单元测试写得像复读机（`assert result is not None` 之类无意义断言）
- 说"这个功能已经实现"，但你点界面上没有入口

## 第 1 章 会话标准流程（每次开发都照做）

每次坐下来写代码，都走这 7 步。熟练后约 2 分钟准备 + 3 分钟收尾，但能省掉大量返工。

### 步骤 1：开场（让 AI 加载记忆）
```
请先读以下文件，然后告诉我项目当前状态与你理解的技术约束：
- AGENTS.md
- docs/PROGRESS.md
- docs/API.md（只看与本任务相关的部分）
- docs/SCHEMA.md（只看相关表）
读完后用 5 句话总结：项目做什么、当前完成到哪、下一步是什么、有哪些硬约束。
不要写任何代码。
```

### 步骤 2：下达任务卡（一次一张）
```
本次任务：S3-2 检索服务（见 docs/PLAN.md 的任务卡）
目标：实现 向量检索 + 全文检索 + RRF 融合 三层检索
产出文件：backend/app/ai/rag/retriever.py、tests/test_retriever.py
约束：只新增上述文件，不要修改其他已有文件；不要引入新依赖，除非先说明理由
先给我一个执行计划（改哪些文件、每个文件做什么、怎么验证），等我确认后再写代码。
```

### 步骤 3：审计划（这一步不能省）
重点看三件事：
1. 它要改的文件是否**超出了任务卡范围**？超了就砍。
2. 它是否用了**不存在的依赖/字段**？对照 `requirements.txt` 和 SCHEMA.md 检查。
3. 它是否遗漏了**错误处理 / 边界情况**（空结果、超时、空知识库）？补上。

### 步骤 4：执行
小步走。如果 AI 一次输出超过 300 行新代码，要求它拆成两次：先接口 + 骨架，再实现细节。

### 步骤 5：验收（必须动手跑）
- 后端：`pytest tests/test_xxx.py -q`、`curl` 打接口、`psql` 查库
- 前端：浏览器点一遍主流程 + 刷新页面看状态是否持久
- 数据：`SELECT count(*) FROM note_chunks;` 确认真的入库了
- **把输出结果发给 AI**，让它确认或修复

### 步骤 6：收尾（让 AI 更新记忆）
```
任务 S3-2 已完成并通过验收。请：
1) 更新 docs/PROGRESS.md：把 S3-2 标记完成，记录实际产出文件与遗留问题
2) 如接口有变化，更新 docs/API.md 对应条目
3) 如新增了环境变量/依赖，更新 .env.example 与 requirements.txt
4) 生成一条符合 Conventional Commits 的 commit message（feat/fix/docs 前缀）
不要修改业务代码。
```

### 步骤 7：提交
```bash
git add -A
git commit -m "feat(rag): 实现向量+全文+RRF混合检索"
```

> **每周结束时**：打一次 tag（`git tag m2-rag-done`），给自己写 3 行周报（完成 / 卡点 / 下周）。周报是你后期论文"工作量说明"的原始材料。

## 第 2 章 仓库的"记忆系统"：5 个文件让 AI 不失忆

长周期项目最大的敌人不是技术难度，是**AI 的上下文丢失**。解决办法是把"记忆"从对话里搬到文件里。

| 文件 | 作用 | 谁维护 | 更新频率 |
|---|---|---|---|
| `AGENTS.md` | 项目宪法：技术栈、目录结构、编码规范、禁止事项、验收习惯 | 你（附录 A 有完整模板） | 一次写好，重大变更时改 |
| `docs/PROGRESS.md` | 进度看板：每个任务的状态、产出文件、遗留问题 | AI 每次任务后更新 | 每个任务 |
| `docs/API.md` | 接口契约：路径、方法、入参、出参、错误码 | AI 随接口开发更新 | 每次改接口 |
| `docs/SCHEMA.md` | 数据模型：表、字段、类型、索引、枚举值 | 你自己定，AI 只能读 | 需求变更时 |
| `docs/DECISIONS.md` | 决策记录：选型理由、放弃的方案、为什么 | 你（关键决策） | 不定期 |

### 为什么这 5 个文件比"把代码全贴给 AI"更有效

- **token 效率**：贴全量代码要几万 token，读 5 个文档只要几千。
- **一致性**：API.md 就是前后端的共同语言，AI 不会一边写 `note_id` 一边写 `noteId`。
- **可交接**：换工具（Cursor → Claude Code）、换电脑、隔两周回来，加载文档就能续上。
- **论文素材**：DECISIONS.md 直接就是论文"系统设计"章节里"方案选型"部分的草稿。

### 一个重要习惯：先让 AI 读，再让 AI 写

永远不要让 AI 凭记忆改代码。会话开头加一句：

```
动手前，请先用 grep/read 查看与本次任务相关的现有文件，确认现有实现方式后再写代码。
对于你引用的每个函数/字段，请标注它来自哪个文件。
```

```
请在当前空仓库中创建 monorepo 骨架，目录如下：
```

- **目标**：把技术栈、规范、禁止事项固化，成为 AI 的常驻上下文
- **产出**：`AGENTS.md`（内容见[附录 A](#附录-a-agentsmd-完整模板复制即用)）
- **提示词（复制）**：
```
请根据我提供的【技术栈与规范说明】（见下方），生成 AGENTS.md。
要求：结构清晰、条目化、可直接被 AI 当作系统约束使用；
必须包含"禁止事项"与"验收习惯"两节。
【技术栈与规范说明】
（把附录 A 的内容贴进来，或让 AI 先据此优化措辞）
```
- **验收**：文件存在且你能对着它说清"这个项目用什么、不用什么"
- **坑**：这条不是形式主义。**AGENTS.md 写得好坏，直接决定后面 60 个任务里 AI 的代码风格一致性**

#### S0-3 写契约文档：SCHEMA.md + API.md（先写，不写全）

- **目标**：把数据库表结构与接口清单草稿落盘（**这是整个项目最重要的一次性投入**）
- **产出**：`docs/SCHEMA.md`、`docs/API.md`
- **提示词（复制）**：
```
请把《个性化学习智能体-毕业设计完整方案.md》第 5 章的表设计整理成 docs/SCHEMA.md：
1) 按模块分组（用户/知识组织/笔记文件/题库错题/练习掌握度/对话引用/Agent运维）
2) 每张表列出：字段名、类型、是否可空、默认值、说明、索引
3) 单独一节说明枚举值（错因类型、题目来源、任务状态、角色等）
4) 不要写 SQL，只写 Markdown 表格
然后从第 6 章和附录 B 整理 docs/API.md：
1) 按模块分组列出接口：方法、路径、入参、出参概要、权限要求
2) 标注哪些接口是 SSE 流式、哪些是异步任务
3) 不确定的地方标注 "TODO 待定"，不要自己编字段
```
- **验收**：两份文档你自己通读一遍，命名风格统一（选 `snake_case` 还是 `camelCase`，**定死**）
- **坑**：AI 会给你编出方案里不存在的字段。**每一条都要对照方案文档核一遍**，这是唯一值得花两小时人工校对的地方

#### S0-4 起基础服务（Postgres + pgvector / Redis / MinIO）

- **目标**：`docker compose up -d` 一键起三个服务，且 pgvector 扩展可用
- **产出**：`deploy/docker-compose.dev.yml`、`deploy/README.md`、连通性自测脚本
- **提示词（复制）**：
```
请创建 deploy/docker-compose.dev.yml，包含：
- postgres:16 (使用 pgvector/pgvector:pg16 镜像)，端口 5432，数据卷持久化
- redis:7-alpine，端口 6379
- minio，端口 9000/9001，自动创建 bucket
所有密码从环境变量读取，提供 .env.example。
另写 scripts/check_services.py：连接三件套并输出"OK/失败原因"。
写完后告诉我启动与验证的完整命令。
```
- **验收**：
  ```bash
  docker compose -f deploy/docker-compose.dev.yml up -d
  python scripts/check_services.py      # 三个 OK
  docker exec -it <pg容器> psql -U postgres -c "CREATE EXTENSION IF NOT EXISTS vector;"
  ```
- **坑**：Windows 上卷路径要写成 POSIX 风格或命名卷；pgvector 扩展**必须在建表前**创建（放到初始化 SQL 里）

#### S0-5 后端最小可运行 + 配置与日志基础设施

- **目标**：FastAPI 能起、`/health` 返回、配置从 `.env` 读、统一异常与响应格式、结构化日志
- **产出**：`backend/app/main.py`、`core/config.py`、`core/logging.py`、`core/exceptions.py`、`requirements.txt`
- **提示词（复制）**：
```
请创建 FastAPI 项目骨架，严格遵循 AGENTS.md。要求：
1) app/main.py：创建 app、注册 /health、CORS（从配置读允许来源）
2) core/config.py：用 pydantic-settings 读取 .env（DATABASE_URL/REDIS_URL/MINIO_*/LLM_API_KEY/LLM_BASE_URL/...）
3) core/logging.py：结构化日志，带 trace_id（用 contextvar + 中间件注入）
4) core/exceptions.py：统一异常基类 + 全局异常处理器，返回 {code,message,trace_id}
5) 统一成功响应结构（在 schemas/common.py 定义）
6) requirements.txt 固定版本号
先给执行计划，确认后写代码。不要实现任何业务功能。
```
- **验收**：`uvicorn app.main:app --reload` 起来，`curl localhost:8000/health` 返回正常；故意访问不存在路由，错误格式符合约定
- **坑**：让 AI 把 trace_id 中间件和日志打通，**后期排查全靠它**，别省这一步

#### S1-2 结构化切片器（关键算法，必须自己看懂）

- **目标**：把解析结果切成"检索原子块"，题目一题一块、笔记按标题切
- **产出**：`backend/app/ai/rag/chunker.py`、`tests/test_chunker.py`
- **提示词（复制）**：
```

1) 检测到连续"题号+题干"模式（如 1. / （1） / 【例2】）时，一题一块，题目与其答案/解析尽量同块（同块上限 800 token）
```

## 第 12 章 让 AI 干活时最容易翻车的 12 个地方

| # | 翻车点 | 表现 | 预防 |
|---|---|---|---|
| 1 | **幻觉 API** | 调用 `langchain.xxx` 里不存在的类、用了 pgvector 没装的算子 | 让它列出用到的每个依赖并核对 requirements.txt |
| 2 | 切片偷懒 | 固定长度硬切，题目被切碎 | S1-2 必须人工看切片结果 |
| 3 | RRF 写错 | 用分数相加代替排名倒数 | 要求贴出公式并写单测验证排序 |
| 4 | 中文全文检索失效 | 直接用 `to_tsquery('chinese', ...)`，或手写 bigram 精度差 | 明确要求用 jieba 分词写 tsv |
| 5 | 向量维度不匹配 | 模型输出 768，表建 1024 | 建表时核对，插入时加断言 |
| 6 | N+1 查询 | 列表页每条记录单独查一次库 | 代码审查时专门查循环里的查询 |
| 7 | 流式被缓冲 | SSE 变成一次性返回 | Nginx `proxy_buffering off` + 后端不压缩该响应 |
| 8 | 掌握度全 0 或全 1 | clamp 漏了 / 初始值错 | 单测 + 真实数据核对分布 |
| 9 | 组卷约束静默失效 | 难度分布不满足但不报错 | 要求约束失败必须返回原因 |
| 10 | 异步任务重复执行 | 重复投递导致重复入库 | 幂等设计 + 唯一约束 |
| 11 | PDF 中文变方块 | 服务器没字体 | 字体打进镜像 + 部署后实测导出 |
| 12 | AI 越改越乱 | 每次让它改，都顺手重构别的模块 | 每次明确"只改这几个文件" |

**通用兜底**：每个里程碑结束做一次"冷启动检查"——`git clone` 到新目录，按 README 跑一遍。跑不起来说明有隐式依赖（本地路径、未提交文件、手工改过的配置）。

## 第 13 章 什么必须你自己做（AI 不能替）

| 事项 | 为什么必须你来 |
|---|---|
| **技术选型与架构决策** | 答辩会问"为什么用 pgvector 不用 Milvus"，AI 给不出你的理由 |
| **数据库表结构与字段语义** | 这是系统的"骨架"，AI 编字段会导致后期全面返工 |
| **知识点树的人工校对** | 内容正确性 AI 保证不了，且这是系统质量的上限 |
| **自测用例的标准答案** | 让 AI 生成标准答案 = 自己给自己判卷，抽查直接失效 |
| **Prompt 的最终定型** | 可以 AI 起草，但效果判定与取舍必须你来 |
| **关键算法的理解** | RRF、掌握度更新、组卷打分、遗忘曲线——要能手推、能口述 |
| **抽查结果的分析** | AI 会替你美化数据，那是学术不端 |
| **论文正文撰写** | 观点、逻辑、自我批评只能是你的 |
| **真实使用感受的收集与解读** | 只有你自己用得出来 |
| **每周进度判断与砍需求决策** | 什么时候启动 Plan B，只有你能决定 |
| **划定"现成 vs 自写"的边界** | AI 天然倾向于"我帮你写一个"；哪个该复用、哪个必须自研（论文创新点），判断权在你 |

> **一个实用平衡**：让 AI 干"有明确对错、能自动验证"的活（CRUD、接口封装、测试、样式）；自己干"没有标准答案、需要判断"的活（架构、标注、调优、写作）。这条线划对了，AI 是 5 倍效率；划错了，是在给未来的自己挖坑。

```markdown
## 1. 项目一句话
面向高中生的个性化复习系统：个人知识库可溯源问答（RAG）+ 错题诊断 + 掌握度驱动的组卷与复习计划 + Agent 多步任务。

- 文档解析：Docling 或 Marker（PyMuPDF 兜底）；中文分词：jieba

- 新需求先找成熟库/API；只有论文创新点那 9 块自己实现
- 擅自引入新依赖前必须先说明理由并等确认
- 不引入需要本地下载大模型的依赖（除非明确要求）
- 任何"手写通用能力"（分词、分页、认证、定时、PDF 渲染、JSON 修复）都要先确认有没有现成库

## 3. 目录约定

## 4. 编码规范
- 分层：路由只做参数校验与调用；业务逻辑在 services；AI 调用只在 ai/ 层
```

### B3 docs/DECISIONS.md（论文选型章节的草稿）
```markdown
## D-003 向量库选型：pgvector 而非 Milvus
- 日期：2026-02-20
- 背景：需要同时存储关系数据、全文索引与向量
- 备选：① pgvector ② Milvus ③ Elasticsearch + 向量插件
- 决策：pgvector
- 理由：单库降低部署与运维复杂度；数据量级（<50 万 chunk）下 HNSW 性能足够；
       过滤条件（user_id/subject_id）可与向量检索下推到同一条 SQL，避免"先粗排再过滤"导致的召回损失
- 代价：超大规模（千万级）下性能不及专用向量库；不支持复杂多路融合算子
- 验证：S1-4 实测 P95 检索延迟 < 120ms（10 万 chunk）

## D-004 图片/试卷识别：多模态大模型 API 而非 PaddleOCR
- 日期：2026-02-25
- 背景：需要把学生拍照的数学题识别为可编辑的 LaTeX 文本
- 备选：① 多模态大模型 API（Qwen-VL / GLM-4V / 豆包视觉） ② PaddleOCR + 公式识别模型拼装 ③ 自训模型
- 决策：多模态 API
- 理由：整题识别一步到位，公式直接输出 LaTeX；无需安装 paddlepaddle（规避 Windows 编译与 Python 版本适配问题）；
       识别效果在数学公式场景明显优于"文字 OCR + 公式模型"的拼装方案
- 代价：按量付费；数据需出网；超长试卷有 token 上限
- 验证：S4-1 用 20 道真实题目对比，人工统计识别可用率（记录到自测文档）

## D-005 PDF 导出：Playwright 而非 WeasyPrint
- 日期：2026-02-25
- 背景：需要把组好的试卷导出为可打印的 A4 PDF（含中文与数学公式）
- 备选：① Playwright（浏览器打印） ② WeasyPrint ③ reportlab 手工排版
- 决策：Playwright
- 理由：用浏览器内核渲染 HTML/CSS，中文字体与 KaTeX 公式表现与网页一致；
       WeasyPrint 在 Windows 上依赖 GTK 运行库、Docker 镜像里中文易缺字体变方块；reportlab 排版成本过高
- 代价：镜像需要预装 chromium（体积 +约 300MB）；渲染比纯 Python 方案慢
- 验证：S5-3 导出后用 pdfplumber 抽文字，确认中文与公式未丢失；打印实测可读
```
