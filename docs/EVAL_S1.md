# S1-7 自测与效果抽查

> 本文所有数字来自 2026-10-21 本机真实运行，不是估算。
> 数据集：`eval/datasets/qa_set.jsonl`；结果：`eval/results/s1-7-*.json`。

## 1. 数据

- 30 条 = 20 条应答题 + 10 条应拒题。
- 覆盖现有 7 个 note（101–107），共 83 个 chunk；note 107 为合成样张，已标注为合成。
- gold 的标注方式：AI 阅读 chunk 内容做**预标注**，用户逐版确认；因此本文不写成“纯人工标注”，避免夸大标注独立性。
- 预标注参考了候选清单，存在选择偏差：`hit@5` 只能说明“当前流程能命中这版 gold”，不能当作独立泛化指标。
- 应拒题 gold 全部为空；应答题 gold 为非空 `note_chunks.id` 集合。

## 2. 方法

三组配置只在检索层不同：

| 配置 | 检索 | 是否跑回答 |
|---|---|---|
| `vector` | pgvector 向量召回 top20，取前 5 | 否 |
| `hybrid` | 向量 + 全文 RRF 融合 top20，取前 5 | 否 |
| `hybrid_rerank` | 融合候选 30 条，qwen3-rerank 后取前 5 | 是，生产链路 |

- `top_n=5`；`hit@5` / `MRR@5` 的分母为 20 条应答题，应拒题不参与。
- 引用精确率 = `|引用 chunk ∩ gold| / |引用 chunk|`；被拒答或应拒题不参与引用平均。
- 引用命中率 = 应答题中至少引用一个 gold 的比例。
- 拒答准确率 = `(TP+TN)/30`；混淆矩阵按“应拒 / 实际拒”统计。
- 回答指标只在 `hybrid_rerank` 上跑；vector/hybrid 不调用 LLM。
- 纯向量配置的延迟复用同一次混合检索调用，是**保守口径**；不是单独起一条纯向量 SQL 的耗时。
- 回答链路内部会再检索一次，因此 `hybrid_rerank` 的检索指标与回答延迟是两次检索，不是同一次。

复现命令（仓库根目录）：

```bash
.venv/Scripts/python.exe eval/run.py --dataset qa_set --config vector --skip-answer
.venv/Scripts/python.exe eval/run.py --dataset qa_set --config hybrid --skip-answer
.venv/Scripts/python.exe eval/run.py --dataset qa_set --config hybrid_rerank
```

## 5. 与 S1-5 的差异

- S1-5 是 10 条问题 + 关键词命中，不是 gold chunk 口径；S1-7 是 30 条 + chunk 级 gold，数字不能直接和 S1-5 的“命中率”混用。
- S1-5 的 rerank 四路对比仍有效；S1-7 只比较 vector/hybrid/hybrid_rerank 三配置。
- S1-7 的 `hit@5=1.000` 受预标注选择偏差影响，不能据此宣称“检索已经泛化到任意问题”。

## 6. 已知局限

1. 样本只有 30 条、语料只有 83 块，统计意义有限。
2. gold 由 AI 预标注、用户确认，且参考了候选清单；`hit@5` 偏高，不能外推。
3. `q004`/`q005`/`q009` 属弱证据题：语料只有性质/例题，没有直接定义；这三题的数字要谨慎解释。
4. 引用精确率只衡量“引用块是否在 gold 内”，不衡量答案文字是否数学正确；答案正确性仍需人工抽查。
5. 纯向量延迟复用混合检索调用，偏保守；不是严格隔离的纯向量 SQL 基准。
6. 回答链路内部重复检索一次，`hybrid_rerank` 的检索延迟和回答延迟不是同一次调用。
7. `citation_invalid` 的拒答会消耗 LLM token；当前指标把这类 token 计入平均，成本口径偏保守。
8. 未覆盖多轮、超长文档、图片/公式 OCR、真实学生数据；不得把本结果当成生产 SLA。
